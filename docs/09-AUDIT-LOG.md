# 09 · 审计日志（五道闸怎么跑、看到什么算坏）

> 本文件是给**接手实现的 agent** 看的操作手册，不是给用户的总结。
> 读完它你应该能做到：在仓库里任意一次改动之后，用一条命令判定「规格书还能不能信」，
> 并且在它报警时知道该修哪一份文件、不该改哪一条数值。
>
> 本文件自身也受铁律约束：不出现代码字面量，不引用未核实的上游数值。
> 上游数值的唯一来源始终是 `docs/02-CONSTRAINTS.md`；本文件只讲**怎么检查**，不讲**限制是多少**。

## 1. 一条命令

```bash
node tools/audit.mjs          # 五道闸全跑
node tools/audit.mjs docs     # 闸 1~4：码点、代码块、表格、跨文件引用
node tools/audit.mjs json     # 闸 5：catalog/limits.json 结构不变量
node tools/audit.mjs exit     # 闸 6：tools/roundtrip.mjs 退出码契约
```

退出码：

| 码 | 含义 | 你该做什么 |
|---|---|---|
| 0 | 全部通过 | 可以继续，可以 commit |
| 1 | 有 findings | 看输出的 `文件:行号  原因`，逐条修；**不许**为了让命令变绿去删测试或放宽判据 |
| 2 | 用法错 | 子命令拼错；改命令行，不改脚本 |

findings 输出按文件名字典序、再按行号排序，每行一个。最后一行是总数。

> 为什么是这条命令而不是五个脚本：这五项检查在本项目里被手工跑过几十次，
> 每次都散落在 `/private/tmp` 下的临时文件里，会话一结束就没了，
> 于是下一次改动又只能「改完看着像就过了」。审计一旦不能重复执行，就等于没有审计。

## 2. 五道闸各测什么

| 闸 | 函数 | 抓过什么真实事故 |
|---|---|---|
| 1 可疑码点 | `checkCodepoints` | U+FFFD 替换符混进正文（内容在某次编码中被 lossy 化过，原文已丢失）；U+2028/U+2029 冒充换行，让整份 md 看起来行数不对；私有区字符（PUA）是字体回退留下的鬼画字，人眼和 diff 都看不出来 |
| 2 代码块成对 | `checkFences` | 多出一个或半个开栏，使文末的「一句话优先级」「任务依赖速览」被当成代码块吞掉，渲染时看不见 |
| 3 表格列数 | `checkTables` | 单元格里一个未转义的竖线，把 3 行表渲染成 5 列，**错位但不说谎**：值还在，只是落到了错误的列 |
| 4 跨文件引用 | `checkRefs` | 写的 `02 §1.5` 在 02 里不存在（章节被重排之后引用没跟着改），读的人按图索骥找不到，只好「猜一个大概的」 |
| 5 catalog 不变量 | `checkJson` | 某个 provider 的 `usageEndpoint` 被置成 null 却没留下 `usageEndpointReason`，代码从此分不清「上游没有这个端点」和「我们还没去看」 |

第六道 `checkExit` 不属于规格书，它保护的是**审计工具自己的可信度**：审计工具先生成
一个 base64 往返副本、再跑校验，如果 `roundtrip.mjs` 的退出码约定变了，
所有「我核对过了」就都会变成空话，而没有任何一道闸会报警。

## 3. 每道闸的判据与它的天花板

### 3.1 可疑码点（`checkCodepoints`）

遍历仓库里 `.md`、`.mjs`、`.js`、`.ts`、`.json` 五类文件（跳过 `node_modules`、`.git`、
`dist`、`coverage`），逐行逐字符盘点。

| 码点 | 判据 | 为什么是坏 |
|---|---|---|
| U+FFFD | `code === 0xfffd` | 只有在解码已经丢信息时才会出现。文件里有它，说明**已经有字节被丢了**，不是错字 |
| U+2028 / U+2029 | `0x2028`、`0x2029` | 它们在 JS 里是换行但会打断字符串字面量，在编辑器里看着像空格。混进来几乎必然来自复制粘贴 |
| C0 控制符 | `code < 0x20` 且不是 `9`/`10`/`13` | 制表、换行、回车以外的控制符没有任何合法用途 |
| 私有区 | `0xe000 <= code <= 0xf8ff` | 字体回退字形。渲染出来像是某个字，复制出来是另一个码点，grep 不到 |

**每行只报第一条**（命中就 `break`），因为一个被整体编码损坏的 i 会一行内全都是坏字符，
报满整屏没有新增信息，只会淹没真正的问题行。

私用区判据的天花板：它抓不到「长得像但字不同」——例如 `>` 被替换成全角 `＞`，
或者 a 被替换成西里尔字母的 a（同形异码），这些码点都落在合法的 CJK / 拉丁 Unicode 区段里。
目前这两类变异没有任何闸能抓，只能靠人工；在实现之前，**不要** 声称本闸覆盖了它们。

### 3.2 代码块成对（`checkFences`）

只读 `DOCS` 数组里的九份 md，统计每份文件里行首（trim 后）出现 fence 的次数，
奇数就报。报的行号恒写 `1`，因为 `checkFences` 不知道是哪一行开的头。

半截 fence 的事故形态长这样：末尾的「一句话优先级」表格看上去是正文，实际上文件已经
被当成代码块尾渲染了 —— 而文件本身还在正常 EOF，不报任何错。

**天花板**：假设 fence 里的内容本身写了一个 fence（比如教程里教怎么写 fence），
本闸会把它算成开/关配对错乱进而报**假警**。本项目一直用「四个反引号包三个反引号」绕开，
但闸本身不区分外层 fence 和内层 fence，报警时先人工看一眼是不是嵌套。

### 3.3 表格列数（`checkTables`）

只把「本行以竖线开头，且**下一行**也以竖线开头并匹配分隔行形状」认定为表头。
这样做的代价是：表头的下一行紧接着不是分隔行（中间空了一行，或下一行是普通文字），
本闸就整张表放过——这是本项目里出过的真实事故形态，见 §5 的第 2 条。

判据 `want = sep.split(BAR).length - 2` 依赖分隔行**两端都有竖线**（GFM 允许省略首尾，
本仓库风格不省略）。如果哪天写出一份无首尾竖线的表格，`want` 会少算一列，
于是同表的每一行都会被报一次「多一列」——报出来是错的，近似位置也是对的，
但计数本身不可信，看到「整张表的数据行全报」时先怀疑是写法变了，不是数据变了。

**数据行只报第一处不一致就跳出**（`break`）。理由同一段：一行错位通常是单元格里漏了个
转义，后面每一行都会跟着报，只报首行就足以定位。

**天花板**：转义竖线和代码块内竖线不区分。`| a \| b |` 会被 `split(BAR)` 数成 3 列。
所以判定标准是「**这个仓库的风格里，正文单元格从不写竖线**」；要写竖线就写进代码块，
或者用「、」「/」代替。这条在 `docs/03-DATA-CONTRACT.md §7` 的日志脱敏正则那一行上
已经踩过坑。

### 3.4 跨文件引用（`checkRefs`）

两个概念：

- **标题集合**（`headingKeys`）：只认 二级到四级标题里，**第一个字符是数字**的标题
  （如 `## 7. Google Gemini`、`### 4.3 套餐与配额分档`），取「数字 + 后续点号串」做 key，
  得到 `7`、`4.3`。
- **引用正则**（`REF_LOOKUP`）：只匹配 `0N` + `§` + 数字串的形态，`N` 取 `0`~`8`。产出两个
  分组，组 1 是文件名号（`02`），组 2 是章节号（`1.5`）。

逐个引用去查「被引文件是否真有这个章节号」：

| 写法 | 结果 |
|---|---|
| `02 §1.5` 且 02 有 `### 1.5` | 过 |
| `02 §1.5` 且 02 没有 | 报 `ref 02 section 1.5 has no matching heading` |
| `02 §1` 且 02 只有 `### 1.5`（没有裸 `## 1`） | 报——本闸不做三层匹配 |
| 裸 `§1.5`（不带文件名） | 不查。它属于「本文件内引用」，由人工和 §4 的约定保证 |
| `03 § col4lok` 这类形式不合法的 | 不查，这是 §4 的约定之外的东西 |

**本闸曾经是绿的但什么都没测。** 两个原因叠在一起：

1. 正则里写的是模板字面量 `${SEC}`，而模板字面量**不**做变量替换，它字面匹配「`$` + `{` + `SEC}`」，
2. `+` 的另一处被吃掉，`\d` 少了量词。

于是这条正则几乎永不命中，扫描遍历了所有文件、一条也没报。**「找到 0 条」和「功能没运行」
在输出里长得一模一样**——这就是为什么一个检查必须在**已知坏的输入**上先响一次。

正向用例做满也只能说明它「不禁止正确的东西」，说明不了它「会禁止错误的东西」。

### 3.5 catalog 结构不变量（`checkJson`）

对 `catalog/limits.json` 逐个 provider 验：

- 文件能被 `JSON.parse`；
- 以换行结尾（否则 `git diff` 会把最后一行和下一整段算成同一处改动）；
- 每个 provider 有 `baseUrl`；
- `baseUrlMutable === false`：Base URL 必须锁死。放一句「可自定义 baseURL」进去，
  就有人会把实例托管地址填进 Token Factory 分组，然后积分在没人调用时也在跑（见 `02 §1.9`）；
- `usageEndpoint` 为空时必须带 `usageEndpointReason`。理由见 `03 §7` 的同一行；
- `limits` 每项要么自己带 `source`，要么是「分组对象」、组内每个叶子各自带 `source`
  （`nestedSources` 递归：**叶子**才需要 `[no source]` 标签，分组对象本身不需要）。
  这一条保证任何数值都能回答「谁说的」——`doc` / `doc-local` / `probe` / `user` / `assume`
  必须始终出现在标签位，不允许「因为我记得」这类来源。

**天花板**：本闸只验**形状**不验**真伪**。把 `20` 写成 `200` 它不会报，因为它没有第二份
事实可以对照。真伪只能靠 `docs/02-CONSTRAINTS.md` 的出处栏和 `docs/07-ACCEPTANCE.md`
的夹具防。不要因为 `node tools/audit.mjs` 绿，就以为 catalog 里的数字是对的。

### 3.6 roundtrip 退出码契约（`checkExit`）

对 `tools/roundtrip.mjs` 断言六件事：匹配时退出码 0、不匹配时 1、参数错时 2、
**且参数错时不往 stdout 打任何东西**，成功时 stdout 打 `1`，不匹配时打 `0`。

最后三条不是洁癖：调用方的惯用式是 `out=$(node tools/roundtrip.mjs check ...)` 再判 `out`。
如果参数错时也打 `0`，「我写错了命令」和「文件被改了」在调用方眼里就是同一个结果，
而后者是要停下整个流程的事故。

## 4. 什么算坏 / 什么合法（别自己发明判据）

**坏**：能证实文档和数据不一致的。四个具体类型——

1. 数值自相矛盾（同一条件两处不同数）；
2. 引用的章节不存在（§3.4 抓的）；
3. 表格结构错位（值落到列外）；
4. 声明与夹具对不上（文档说会被拒，夹具里过得去）。

**不坏**（出现这些现象不要据此改文件）：

1. **形状不合我口味**：`ProviderAdapter` 字段名、`RateKind` 枚举大小写、误分类映射表怎么写、
   错误壳认几种、空态显示「—」还是「暂无数据」。
2. **名称和数值不同源**：单个模型开发成表里给了「上下文长度」，`context_length` 却由
   统一下发字段给。两者数值应该是「1:1、`262144`」为基础推断的，不等于就是文档错了。
3. **未验证的判断**：某个模型在某个端点是不是支持某个参数，文档没逐字写，就不算「文档说支持」。
   这是**未验证**，不是**错**。
4. **四家/五家的计数**：`docs/02` 的 §1~§4 是四家，§7 是第五家 Google。看到「四家」先看上下文
   有没有「另外」二字，别一刀切全局替换——那会把「另外四家」改成「另外五家」，反倒造出新错。

只有第 4 类出现时动手，动手前先用 `git log -S` 找到它是哪一轮引入的，
看那轮的变更说明判断是笔误还是刻意。

## 5. 本项目已踩过的坑（闸为什么长这样）

1. **闸 1 只报每行第一条**：一次编码损坏会让整行上百个字符全变成 U+FFFD，逐字符报等于刷屏。
2. **闸 3 的「表头下一行必须是分隔行」**：`docs/01-PRD.md` 附录表格 4 行数据行**没有分隔行**，
   4 行被 md 渲染成一行，读的人在 diff 里看见的是 4 行、渲染出来是 1 行，两边都不算错。
   后来补了分隔行。约定见 `docs/00-README.md §3`。
3. **闸 4 的假绿**：见 §3.4。修好之后立刻拿两样**已知坏**的输入各打一次（不存在的 `§9.9`、
   存在的 `§7.4`），前者 rc=1、后者 rc=0，才算这条闸能用了。
4. **闸 6 的 `0`**：`roundtrip.mjs` 曾是「不匹配就打 `0`」，包括参数错也打 `0`。
   删掉那行之后，参数错变成静默 rc=2；调用方 `out` 为空，不会误判。
5. **`--no-bail`**：根 `package.json` 的 test 脚本曾经带 `--no-bail`（失败也继续跑别的包），
   于是某个包挂了、整体还是 0。「五项校验全绿」在那种配置下**从来没被真正证明过**。
   现在脚本是 `pnpm -r test`（默认遇错就停）。

## 6. 已知未覆盖（不要因为 `audit: clean` 就以为都过了）

| 缺口 | 现状 | 补的时候注意 |
|---|---|---|
| 同形异码 / 全角符号 | 无检测 | 抓它需要一份「允许字符集」白名单，误报会很高；先只在 `.ts` 源码上做 |
| 中英粘连词（`UI Must`、`config 值`） | 人工逐个修过，无闸能抓 | 判据要能排除正常英文术语（`Provider`、`Retry-After`），否则整份文档报满 |

| 空的 `test/fixtures/` 目录 | `git ls-files` 看不到（git 不存空目录） | 夹具都以 `FakeUpstream` 的**内存代码**形式存在于测试文件内，没有独立 fixture 文件——这与 `07 §0` 描述的「夹具基础设施」是一致的，但意味着每个用例都要自己在测试里搭 |

### 6.1 闸绿到底证明了什么（这一节过期过一次，留作例子）

本节此前的写法是「插件本体还不存在，`packages/plugin-dsh/src/index.ts` 与 `packages/client-ui/src/index.ts`
各自只有一行 `export const VERSION`」。这句在写下那天是事实，在今天不是：两个包各自有几百行。

**它就是这么烂掉的**：没人改它，因为没人读到它；代码烂了测试会红，文档烂了只会在下一次
有人引用它时安静地误导一次。这一节保留，作为 `audit: clean` 最需要配的注脚——
`audit: clean` 只说明**这五道闸各自测的东西没退化**，它不说明被测的东西覆盖了插件。

当前 `audit: clean` 覆盖到的（真实，可复现）：

- `packages/core`：十进制算价、北京时间日界、epoch 归一、Retry-After 解析、Key 掩码与拒绝前缀、
  IP 级限流分类、断路器的三态与窗口、rollup 折并、快照聚合与脱敏导出、AMD 设置校验及其引用。
- `packages/plugin-dsh`：命令半的名字分派与拒收顺序、凭据接缝的读写与确认重读、
  `apply` 在无 `inject` / `inject` 抛错 / 无读方的三种 ctx 上都能激活。
- `packages/client-ui`：图标四态（绿/黄/红/idle）、`—` 不变成 `0`、图标 id 与主面板 key 相同、
  `client.js` 内联副本与 `src/icon-state.ts` 的 parity。

当前 **`audit: clean` 不等于**：

1. **插件能用**。「能激活」刚在真机上第一次被证实（`473c3e1` 删掉 `inject: ['slots']`），
   在此之前它一直是 `pending (waiting for service: slots)`，装上了也永远不出行。
   这类事闸测不出来：闸跑在 vitest 里，vitest 里的 ctx 是这一仓自己捏的。
2. **能显示额度**。`IconView` 的三行目前恒为形状 D（Host 没在跑）：host 侧没有真实数据源，
   浏览器半拿到空视图就画 `—`。链路通了，账还是空的。
3. **能防 429**。调度器在 `packages/core` 里成立，但没有任何一层把它接进真实请求路径——
   本地代理（T-1-h）还没写。
4. **D-01 的 `fold()` 合并分支**。`packages/core/src/metrics.ts` 里已有一条 rollup 时累加的分支，
   夹具覆盖它需要「同一个上海日分两次 sweep 过期」，我在 `amd-metrics.test.ts` 上试过六轮、
   全部算错 `floor`，最后放弃并在 commit 里写明**没有测**。它现在是被实现读着、而不是被测试守着的。

读到 `audit: clean` 就以为「第一批交付了」，是这份文档里最容易发生的误读。它曾经发生在这里。

### 6.1.1 一段通道史：为什么传输层换了五次

T-2-b 要的是「左栏图标能显示池子状态」。这个「能」被五个不同的东西挡了五次，每次挡住时
周边的测试**都是绿的**，因为每次都是 vitest 里那个假 ctx 比真 ctx 多给了一点东西：

| 方案 | 在 vitest 里 | 在真 DSH 里 | 结果 |
|---|---|---|---|
| `globalThis[CHANNEL_KEY] = channel` | 绿（测试给两半同一个 global） | Host 写的是 Node 的 globalThis，页面读的是 Electron renderer 的 window | 两个进程各持一个全局，写得进去、读不到 |
| `ctx.inject(['connection'], …)` + `connection.rpc.handle` | 绿（假 ctx 给了 `connection`） | `connection` 只在 DSH 自己的 client bundle 里 provide，profile 装的插件拿不到 | 注入永不回调，图标画 `—`，host 其实健康 |
| `window` 事件（现方案） | 绿 | 绿（`e66c31c` 起真机上桥挂上、页面派发成功） | 无鉴权，页内已有脚本可冒充 host；已在 docs/09 §6.1 与 channel.ts 头注释写明 |
| 挂到 `globalThis` 上发声 | 绿（假 ctx 给了 `connection`） | `apply()` 抛 `where.addEventListener is not a function`，cordis 把 entry 整个摘掉，图标变黑、重开插件消失 | 已退回 `window` 事件（`225e244`） |

这五条记录下来的用处不是“看我们多曲折”，而是：**凡涉及 DSH 生命周期或跨半边界的假设，
先去 `app.asar` 读实现再写**。前几次我都是照着参考包的形状抄的，形状抄对了，括号里的 API 不存在。

第五条比前四条更值得记，因为它不是括号里的 API 不存在，而是**我用来验证的方式本身不会失败**：

- 我把 `globalBridge()` 改回 `return globalThis`，跑全量，**56 个用例仍然全绿**。原因是此前所有
  用例都显式传了 `target`，那个默认分支一次都没被执行过。一个从未执行的分支，改对改错都测不出来，
  而测试全绿会让人以为“改前是错的、改后是对的”这件事已经被证明了。
- 之后补的两条用例（不传 `target` 时是否找到 window、没有 window 时是否安静返回）一加上，
  同样的变异立刻**红 2 条**，错误逐字是用户在真机上看到的那句。

同类的第二次也发生了：`MultiPoolPanel` 里一度有两个 `React.useEffect`，第一个是旧的。
面板一直停在初值 `not asked yet`，而 9 条 `node:test` 全绿——因为绿色测的是第二个 effect 的
字符串，而屏幕上是第一个页签的状态。两边都“对”，只是从没在同一个组件里跑过。

所以这个文件里要记住的不是“小心写代码”，而是两件事：

1. **默认参数 + 可选透传**这条缝上，必须有一条用例真的不传那个参数走一遍，否则那个分支不存在。
2. 面板上给人看的那一行，必须是**“我走到了哪一步”**，而不是“我要的答案”。答案为空时，
   前者仍然是一整句话；后者只会是初值，而初值和“没跑到”长得一模一样。

### 6.2 一个闸测不了的东西：来源标签恰不恰当

`catalog/limits.json` 里每个叶子都带 `source`，白名单是 `doc` / `doc-local` / `probe` / `user` / `assume` / `unknown`。
闸只验**标签在不在白名单里**，不验**这个数字配不配得上这个标签**。

- 把 NIM 的 40 RPM 的 `source` 从 `user` 偷偷改成 `doc`：闸绿。但这等于宣称 NVIDIA 官方文档逐字写过 40，
  而事实上没有。下游 agent 会把它当硬事实用。
- 把一个 `assume` 的保守系数写成 `doc`：同上。
- 把 `rpmLimit` 的 `value` 从 20 改成 20 以外的任意数，只要仍是数字：闸绿。

这个缺口**不打算**用脚本补。判据要求「这个数字能在文档里找到逐字出处」，需要人去读原文、
记下出处行号，脚本只能验**出处行号指向的那行文字里有没有这个数字**——而 `docs/02`
本身就是引用原文的二手整理，验它只能验出自洽，验不出真伪。

替代做法只有一条纪律：**任何从 `doc` / `doc-local` 之外的标签升格的改动，
必须在 commit message 里写出原始出处**（URL、文档名、抓取日期）。

### 6.3 夹具编号有三种互相冲突的记法

- `07-ACCEPTANCE.md` 的夹具是**二级标题分组、三级标题编号**（`## A · AMD…` 下面是 `### A-01`）；
- `04-SCHEDULER.md` 的调度矩阵是**表格第一列**（`| S-01 | … |`），不是标题，所以任何「扫 `### S-` 标题」的脚本都找不到它；
- `06-TASKS.md` 的验收字段是**正文里的裸编号**（`- **验收**：Z-01`、`A-01 ~ A-08`），也不带标题前缀。

这三类的正确收集方式各不相同，闭包脚本必须分别绑：

- 任务号 `T-x-y`：扫 `06-TASKS.md` 的三级标题；
- 夹具号 `A-01` 到 `Z-07`：扫 `07-ACCEPTANCE.md` 的三级标题。
  不要按「前缀是字母且不是 T/S」来筛，否则 `Z-01` 会被误判成别的家族；
- 调度矩阵 `S-01` 到 `S-20`：是 `04-SCHEDULER.md` 第九节的**表格第一列**，不是标题。
  只扫标题的脚本会把 `06` / `07` / `08` 里对 S 系列的引用全算成悬空。

### 6.4 上游实测与文档不符的地方（2026-11-20）

doc 转到 live 端点的几步里，有两条 §1.3 / §1.6 的说法被真响应打了折扣。
这里把它们照实记下来，**原文不动**：文档写的是官方文档怎么说，这一节写的是我们真看到了什么。
两者都不是「错」，但读者必须知道哪一条已经被自己的眼睛过了一遍。

#### 6.4.1 `GET /v1/usage` 的 200 响应里没有 `X-RateLimit-*`

带真实 `rc-` Key 请求 `GET https://developer.amd.com.cn/radeon/api/v1/usage?include_recent=true`，
得到 `HTTP/2 200`，响应头**共 6 个**，逐个是：

| 头 | 值的样子 |
|---|---|
| `date` | RFC 1123 时间 |
| `content-type` | `application/json` |
| `server` | `nginx` |
| `vary` | `Accept-Encoding` |
| `x-cloud-trace-context` | 十六进制串 `/` 数字 `;o=1` |
| `x-trace-id` | 与上面 trace 段同值 |

**没有** `X-RateLimit-Limit-User-RPM`、**没有** `X-RateLimit-Remaining-User-RPM`、**没有** `X-RateLimit-Reset`，
也没有任何 `X-RateLimit-*User-Daily-USD`。

这不等于 `docs/02` §1.3 写错了。§1.3 的原文是「每次**成功调用**都会在响应头里带上当前计数」，
而 `/v1/usage` 是**查询用量的那一次调用**，不是「成功调用」所指的业务调用。
体面的读法是：用量端点的职责在 body 里把数字给你，头部那七个是 `/v1/chat/completions` 的附带品。

**assume（未核实）**：七个 `X-RateLimit-*` 头的真身出现在 `/v1/chat/completions` 的 200 响应上。
这一条本轮**没有**去证：证它要发一次真的补全请求，即要花用户的 pts。用户未授权花额度，我不做。

对代码的约束（无论上面那条 assume 最后是否成立，都成立）：

- 读配额数字**只能**读两处——`/v1/usage` 的 body，或业务调用响应头里的 `X-RateLimit-*`；
- **不能**假定 `UsageResult` 里能顺带捞到头信息。`amd-usage.ts` 现在只解析 body，这是对的；
- 若要落「响应头优先于 body」的规则（docs/04 §9.2 的意思），落点只能是 chat 那条路径的响应处理，
  不能在 usage 轮询里假装自己拿到了头。

#### 6.4.2 `rpm_limit` 实测是 20，`docs/02` §1.6 的示例写的是 30

`docs/02` §1.6 的 JSON 示例里 `rpm_limit: 30`、`daily_cost_limit_usd: 10`，本机实测是 `rpm_limit: 20`、
`daily_cost_limit_usd: 1`。**两者不矛盾**：§1.6 的示例本就是「一个账号的样子」，且官方原话是
「不同账号的限额不同……请从这个接口读取你自己的限额，不要假设」。实测 20 恰好与 `catalog/limits.json`
的 `limits.rpmAccount: 20`、`docs/04` §2.2 的 `min(20,30)` 一致——说明那两处当初取的是保守值，不是拍脑袋。

派生的后果值得记一句：`assumedExternalClients` 假设的「外部客户端」在本机这台机器上未必存在，
但它是**保守系数**不是**测量值**，20 × 0.85 ÷ 1.5 = 11 仍然是「假设值」，标签不该从 `assume` 动。

#### 6.4.3 怎么复核这一节

一条请求、只看头名、不打印任何值、不打印 body：

```sh
curl -sS -o /dev/null -D - \
  -H "Authorization: Bearer $AMD_API_KEY" \
  'https://developer.amd.com.cn/radeon/api/v1/usage?include_recent=true' \
  | grep -i '^x-ratelimit-'
```

- 有输出 → 这一节过时了，回到 §1.3，把头名补全；
- 无输出 → 与本节一致，§1.3 的原文仍只当「官方文档怎么说」读。

body 里有 `organization_id`、`project_id` 和账号用量，**不要**贴进仓库、不要粘进对话。

#### 6.4.4 `credentials` 接缝的实测形状（2026-11-21）

`docs/06` 的 T-2-e 一开始只是读 `@deepseek-ai/dsh-credentials` 与
`@deepseek-ai/dsh-credentials-local` 的源码写下的假设。后来用 asar 把这两个包（连同
`cordis`、`yaml`、`chokidar`、`readdirp`、`dsh-atomic-write`、`dsh-home-paths`、
`dsh-launch-environment`、`dsh-brand`、`schemastery`、`cosmokit`）从**装在本机的 DSH.app**
里抽到 `/tmp`，直接用这份编译产物 `new LocalCredentialProvider(...)` 跑了一遍真文件往返，
下列四条从「源码里读到」变成「跑出来是这样的」。

探测用的假文档写在 `mkdtemp` 的临时目录里、`mode: 0o600`、结构模仿真文档（`version: 1`；
`refs` 下第一条上方有一段手写注释；另有一条别的插件的 ref；`records` 下一条 `grant`）。
写进去的值是 `rc-` + 一个随机 uuid，**不是任何真 Key**。`~/.dsh/` 一次也没被读写。

| 层 | `describe()` 返回的键 | 有没有预览 |
|---|---|---|
| `file`（`.credentials.yaml` 里真有） | `configured, masked, source, writable` | 有 |
| `env`（继承进程环境） | `configured, source, writable` | 没有 |
| `project-env` / `user-env`（`.env`） | `configured, source, writable` | 没有 |

- `masked` 是**同长度**预览：假 Key `rc-probe-original` 17 个码点，预览也是 17 个。
  把预览里的 `-` 换成 `~`、`•` 换成 `*` 之后，得到的是 17 个 `*`，**一个字符也没露**。
  原因是 `maskCredential` 的规则「至少藏 8 个码点才露头」：这个假 Key 只藏得住 5 个
  （17 − 3 位 `rc-` − 5 − 4），于是整串埋掉。真的 `rc-` + 32 字符会露头 8 位、藏 23 位，
  但**这一条没有用真 Key 验过**，也不该用真 Key 去验。
- `unset` 之后再 `describe`，只剩 `{configured: false, writable: true}`；`source` 和 `masked`
  都不见了，所以「已删除」和「从没配过」在**返回形状上**长得一样，区分它们只能靠调用方
  自己记着刚才做了什么。
- **一次 set + 一次 unset 会发两次 `credentials/reference-updated`**，都在 `watch: false`
  时发出——说明这两条来自 provider 自己的 `notifyUpdated`，不是 chokidar 看见文件变了。
  ⇒ 订阅这个事件的读方，**每个写操作要重读一次，不是每次编辑重读一次**。
  本插件的 `watchKeyStatus` 因此有一句「可能比写入次数多读一次」，而不是含糊的「随事件重读」。
- **`unset` 会把该键上方的手写注释一并删掉**，同文件别的 ref 与 `records` 里的 `grant`
  不受影响。这是 `deleteSectionEntry` 里显式 `map.commentBefore = null` 的行为（理由写在
  `packages/plugin-dsh/src/credentials.ts` 的注释里），不是意外。对本插件的约束是：
  插件只、并且只能读写 `AMD_API_KEY` 这一条；那条注释的归属是 DSH 或用户，不是本插件，
  所以界面**不能**承诺「删掉 Key 后注释还在」，也**不做**替别的插件恢复注释的事。
  这一条留在本节的意义只是：真发生的时候，知道是谁干的、以及不是 bug。
